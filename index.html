Cómo se mide DevOps: las 4 métricas DORA

🚀 Frecuencia de despliegue

Cada cuánto liberas a producción. Más frecuente = más ágil (tú: despliegues diarios).

⏱️ Lead time for changes

Cuánto tarda un cambio desde el commit hasta producción.

🔧 MTTR — tiempo de recuperación

Cuánto tardas en restablecer el servicio tras un fallo.

❌ Change failure rate

% de despliegues que causan un fallo. Menos = más calidad.

SRE en una frase: defines SLIs/SLOs (objetivos de fiabilidad), gastas un error budget cuando fallas, y haces postmortems sin culpa para aprender, no para señalar.

¿Qué es DevOps, en una frase?

Unir desarrollo y operaciones con cultura, automatización y medición para entregar software más rápido y confiable. No es un cargo ni una herramienta: es una forma de trabajar (modelo CALMS).

¿Qué es Infraestructura como Código (IaC)?

Definir servidores, redes y recursos en archivos versionados (Terraform, Bicep) en lugar de configurarlos a mano. Así la infraestructura es reproducible, revisable y auditable, y se despliega igual en cada entorno.

¿Qué miden las métricas DORA?

La salud de la entrega: frecuencia de despliegue, lead time de un cambio, MTTR (recuperación ante fallos) y change failure rate. Son el estándar para medir a un equipo DevOps de alto rendimiento.

Las anotaciones que debes saber explicar

@SpringBootApplication

Marca el punto de arranque; activa autoconfiguración y el escaneo de componentes.

@RestController

Expone la clase como API REST: sus métodos devuelven JSON directamente.

@Service

Contiene la lógica de negocio; es un componente inyectable.

@Repository

Acceso a datos. Con Spring Data JPA casi no escribes SQL.

@Entity

Mapea una clase Java a una tabla (ORM con Hibernate).

Inyección por constructor

Spring "inyecta" las dependencias que la clase necesita: desacopla y facilita las pruebas.

Un microservicio completo, capa por capa

Ejemplo: un servicio de facturas con un endpoint para listar pendientes y otro para crear.

1. Entity — el objeto que mapea a la tabla:

@Entity
public class Factura {
  @Id @GeneratedValue
  private Long id;
  private String concepto;
  private BigDecimal monto;
  private LocalDate vence;
  // + getters / setters
}

2. Repository — acceso a datos sin escribir SQL (Spring lo genera desde el nombre del método):

public interface FacturaRepository
        extends JpaRepository<Factura, Long> {

  List<Factura> findByVenceBefore(LocalDate fecha);  // SELECT ... WHERE vence < ?
}

3. Service — la lógica de negocio, con inyección por constructor:

@Service
public class FacturaService {
  private final FacturaRepository repo;

  public FacturaService(FacturaRepository repo) {  // Spring inyecta el repo
    this.repo = repo;
  }

  public List<Factura> pendientes() {
    return repo.findByVenceBefore(LocalDate.now());
  }

  public Factura crear(Factura f) { return repo.save(f); }
}

4. Controller — expone los endpoints REST:

@RestController
@RequestMapping("/api/facturas")
public class FacturaController {
  private final FacturaService service;

  public FacturaController(FacturaService service) {
    this.service = service;
  }

  @GetMapping("/pendientes")
  public List<Factura> pendientes() {
    return service.pendientes();
  }

  @PostMapping
  public ResponseEntity<Factura> crear(@Valid @RequestBody Factura f) {
    return ResponseEntity.status(201).body(service.crear(f));
  }
}

spring:

Preguntas típicas de Spring Boot

¿Qué es la inyección de dependencias y cómo la hace Spring?

Es dejar que un contenedor (el IoC container de Spring) cree y "entregue" las dependencias que una clase necesita, en vez de que ella las construya. Spring detecta los componentes (@Service, @Repository) y los inyecta — preferiblemente por constructor, lo que desacopla y hace el código fácil de probar (puedes inyectar un mock).

¿Cómo accedes a la base de datos sin escribir SQL?

Con Spring Data JPA: extiendes JpaRepository<Entidad, Id> y ya tienes save, findAll, findById, etc. Además, Spring genera consultas a partir del nombre del método (findByVenceBefore → WHERE vence < ?). Para casos complejos usas @Query con JPQL o SQL nativo.

¿Cómo conecta un servicio Spring Boot con los health checks de Kubernetes?

Con Spring Boot Actuator, que expone /actuator/health/readiness y /actuator/health/liveness. Las probes del Deployment de Kubernetes apuntan a esas URLs: si readiness no responde OK, K8s no le manda tráfico; si liveness falla, lo reinicia. Eso es lo que habilita el zero-downtime real.

¿Cómo se comunican dos microservicios en Spring Boot?

De forma síncrona con WebClient u OpenFeign (llamadas REST), envolviéndolas en un circuit breaker (Resilience4j) para tolerar fallos; o de forma asíncrona por eventos/mensajería (NATS), que los desacopla y los hace más resilientes.

Los conceptos que debes saber explicar

ASP.NET Core

El framework web: multiplataforma (Linux, contenedores), con servidor Kestrel integrado. Es lo que reemplazó al viejo ASP.NET sobre IIS/Windows.

Inyección de dependencias

Viene de fábrica en el framework (no necesitas Spring ni un contenedor externo): registras en Program.cs con AddScoped, AddSingleton o AddTransient.

Entity Framework Core

El ORM: el equivalente de JPA/Hibernate. DbContext es la unidad de trabajo, y las migraciones versionan el esquema (como Flyway o Alembic).

LINQ

Consultas tipadas dentro del lenguaje: Where, Select, Include. EF Core las traduce a SQL. Es lo que más sorprende a quien viene de Java.

async / await + Task

C# fue pionero en esto: Task<T> representa el trabajo pendiente. Igual que en FastAPI, ayuda en carga I/O-bound, no en CPU.

Preguntas típicas de .NET / C#

¿Diferencia entre .NET Framework, .NET Core y .NET 8?

.NET Framework (hasta 4.8) es el clásico: solo Windows, sobre IIS, hoy en modo mantenimiento. .NET Core fue la reescritura multiplataforma y open source. Desde .NET 5 se unificaron los nombres, y hoy vamos por .NET 8 (LTS): multiplataforma, mucho más rápido y pensado para contenedores. Lo que complica una migración no es el lenguaje sino las dependencias solo-Windows (WebForms, WCF, System.Web).

¿Cómo funciona la inyección de dependencias en ASP.NET Core?

El contenedor viene integrado. En Program.cs registras los servicios con un ciclo de vida: Transient (uno nuevo cada vez que se pide), Scoped (uno por petición HTTP — el habitual para servicios y DbContext) y Singleton (uno para toda la app). El framework los inyecta por constructor. El error clásico es inyectar un Scoped dentro de un Singleton: el DbContext queda capturado y se corrompe.

¿Qué es Entity Framework Core y cuándo usarías Dapper?

EF Core es el ORM: mapea clases a tablas y traduce LINQ a SQL, con change tracking y migraciones. Uso Dapper (un micro-ORM) cuando necesito SQL a mano y máximo rendimiento: reportes pesados, consultas muy afinadas o procedimientos almacenados. Conviven bien: EF Core para el CRUD del dominio y Dapper para las consultas críticas.

¿Qué es el middleware pipeline y por qué importa el orden?

Cada petición atraviesa una tubería de componentes que pueden actuar antes y después del siguiente. El orden define el comportamiento: el manejador de excepciones va primero (para envolver todo lo demás), y UseAuthentication siempre antes de UseAuthorization, porque primero se establece quién eres y solo después si tienes permiso. Ponerlos al revés hace que la autorización nunca vea al usuario.

¿async/await en C#: qué resuelve y qué no?

Libera el hilo mientras se espera una operación de E/S (BD, otra API), de modo que el servidor atiende muchas más peticiones concurrentes. No acelera el trabajo CPU-intensivo. Dos errores clásicos: bloquear con .Result o .Wait() (puede provocar deadlock) y el async void, que impide capturar excepciones — salvo en manejadores de eventos, siempre async Task.

¿Qué es LINQ y qué cuidado hay que tener?

Es consultar colecciones con sintaxis tipada del lenguaje (Where, Select, GroupBy); con EF Core se traduce a SQL. El cuidado: distinguir IQueryable (se ejecuta en la base de datos) de IEnumerable (se ejecuta en memoria). Si materializas antes de tiempo, te traes la tabla entera al proceso. Y ojo con el N+1: se resuelve con Include, igual que con JOIN FETCH en JPA.

Componente

Una función que recibe datos y devuelve la UI (JSX). Se compone con otros componentes, como funciones que se llaman entre sí.

No manipulas el DOM: describes cómo se ve la UI para un estado dado y React calcula la diferencia mínima y la aplica.

Añade estado a un componente. El setter es asíncrono por lotes: no leas el valor justo después de escribirlo, usa la forma con función.

useEffect

Sincroniza con algo externo (una API, un timer, una suscripción). El array de dependencias decide cuándo vuelve a correr; y devuelve una función de limpieza.

Identidad estable de cada elemento para no re-crear el DOM. Nunca uses el índice si la lista se reordena o filtra: rompe el estado de las filas.

Extraer lógica reutilizable en una función useAlgo(). Es el mecanismo de reutilización de React (no hay herencia).

Pasar datos a todo un subárbol sin ir prop por prop (prop drilling): tema, usuario autenticado, idioma. Para estado complejo, Redux o Zustand.

Cuando cambia su estado, sus props o un contexto que consume. Optimizar antes de medir es el error más común.

Preguntas típicas de frontend

¿Cuál es la diferencia entre props y estado?

Las props las recibe el componente de su padre y son de solo lectura: son su entrada. El estado es información que el componente posee y puede modificar; al cambiarlo, React vuelve a renderizar. Regla práctica: si el dato lo necesitan varios componentes, súbelo al ancestro común y bájalo por props; si solo lo usa uno, que sea estado local.

¿Qué son los hooks y cuáles son sus reglas?

Funciones que dan estado y ciclo de vida a los componentes de función (useState, useEffect, useMemo, useContext). Dos reglas: se llaman siempre en el nivel superior (nunca dentro de if, bucles o funciones anidadas, porque React los identifica por orden de llamada) y solo desde componentes o desde otros hooks. La lógica reutilizable se extrae en un hook personalizado.

¿Para qué sirve el array de dependencias de useEffect?

Le dice a React cuándo volver a ejecutar el efecto. Vacío ([]) = solo al montar; con variables = cada vez que alguna cambie; sin array = en cada render (fuente clásica de bucles infinitos). Si el efecto abre algo (suscripción, timer, listener), debe devolver una función de limpieza para cerrarlo, o se filtra memoria.

¿Por qué no usar el índice como key?

Porque la key es la identidad del elemento entre renders. Si la lista se reordena, filtra o se inserta al principio, los índices se corren y React asocia el estado del DOM a la fila equivocada: se mezclan valores de inputs y se pierde el foco. Usa un id estable del dato. Con listas estáticas que nunca cambian de orden, el índice es inocuo.

¿Qué es RxJS y qué diferencia hay con una promesa?

Una promesa entrega un solo valor, una vez. Un Observable de RxJS es un flujo que puede emitir muchos valores en el tiempo, es cancelable y se compone con operadores (map, filter, debounceTime, switchMap). Brilla en búsquedas mientras escribes o WebSockets: con debounceTime + switchMap cancelas la petición anterior. El costo es la curva de aprendizaje; por eso Angular incorporó signals para el estado simple.

Porque no bloquea: mientras espera una operación de E/S (BD, red, archivo), el event loop sigue atendiendo otras peticiones y ejecuta el callback cuando el resultado llega. Así, un solo hilo sostiene miles de conexiones concurrentes de E/S.

¿Diferencia entre bloqueante y no bloqueante?

Una operación bloqueante detiene el hilo hasta terminar; una no bloqueante devuelve el control de inmediato y avisa después (callback/promesa). Node es no bloqueante por diseño, por eso conviene evitar código CPU-intensivo que "tape" el event loop.

¿Cuándo elegirías Node y cuándo Java/Spring?

Node para APIs de mucha E/S, tiempo real (websockets) o un BFF en el mismo lenguaje del frontend. Java/Spring para dominios complejos, tipado fuerte y transaccionalidad pesada. No es "uno u otro": elijo por el problema.

Preguntas típicas de FastAPI / Python

¿Por qué FastAPI y no Flask o Django?

FastAPI trae de fábrica lo que en Flask armarías a mano: validación con Pydantic, soporte async nativo (ASGI) y documentación OpenAPI automática, con muy buen rendimiento. Django es excelente para apps con panel de administración y ORM integrado, más "baterías incluidas"; para microservicios/API-first con alta concurrencia de E/S, FastAPI es más liviano y directo. Elijo por el caso.

¿Cómo valida los datos de entrada?

Con Pydantic: declaras un modelo con los tipos esperados y FastAPI valida y convierte cada petición contra él. Si el cuerpo no cumple (tipo equivocado, campo faltante), responde automáticamente 422 Unprocessable Entity con el detalle de qué falló — sin que escribas esa validación.

¿Qué es async/await y cuándo ayuda de verdad?

Permite que una ruta ceda el control mientras espera una operación de E/S (BD, otra API, archivo) en vez de bloquear el proceso. Ayuda en cargas I/O-bound con mucha concurrencia. Ojo: para trabajo CPU-intensivo no acelera (ahí conviene workers o procesos aparte); y si usas un driver de BD síncrono, esa llamada sigue siendo bloqueante.

¿Cómo se documenta la API?

FastAPI genera el esquema OpenAPI a partir de tus tipos y schemas, y expone una UI interactiva en /docs (Swagger UI) y /redoc. Sirve para probar endpoints, compartir el contrato con otros equipos y generar clientes automáticamente — todo sin mantenimiento manual.

Los datos Cursillo de Bases de Datos & SQL

El corazón de casi toda app: guardar y consultar datos de forma correcta y rápida. Tú trabajas PostgreSQL y Oracle a diario (dashboards, reconciliación) — aquí lo estructuras para explicarlo.

Modelo relacional en una frase: los datos viven en tablas (filas y columnas); las tablas se relacionan por claves (una primary key identifica cada fila, una foreign key apunta a otra tabla).

Conceptos que debes dominar

Claves

Primary key: identifica cada fila. Foreign key: relaciona tablas y garantiza integridad referencial.

JOINs

Combinan tablas: INNER (solo coincidencias), LEFT (todo lo de la izquierda + lo que empate).

Índices

Aceleran búsquedas (como el índice de un libro). Clave para el rendimiento; cuestan en escritura.

Transacciones (ACID)

Atomicidad, Consistencia, aIslamiento, Durabilidad. O todo o nada — clave en finanzas.

Normalización

Organizar tablas para evitar datos duplicados e inconsistentes (1FN, 2FN, 3FN).

Problema N+1

Hacer 1 consulta + N por cada fila. Se evita con JOINs o carga anticipada (eager). Clásico con ORMs.

SQL esencial en un ejemplo

-- Facturas vencidas por cliente, con su nombre (JOIN + filtro + orden)
SELECT c.nombre, f.concepto, f.monto, f.vence
FROM   facturas f
JOIN   clientes c ON c.id = f.cliente_id
WHERE  f.pagada = false
  AND  f.vence < CURRENT_DATE
ORDER BY f.vence;

-- Agregación: total pendiente por cliente (solo > 1.000.000)
SELECT c.nombre, SUM(f.monto) AS total
FROM   facturas f JOIN clientes c ON c.id = f.cliente_id
WHERE  f.pagada = false
GROUP BY c.nombre
HAVING SUM(f.monto) > 1000000;

SQL vs. NoSQL

SQL (relacional): estructura fija y transacciones fuertes — ideal para datos financieros. NoSQL: flexible y escala horizontal — para grandes volúmenes o esquema variable.

Pool de conexiones

Reutilizar conexiones abiertas (HikariCP en Spring) en vez de abrir una por request — clave para el rendimiento bajo carga.

Cómo lo cuentas tú: "Modelo y consulto PostgreSQL y Oracle en apps de misión crítica: diseño esquemas normalizados, optimizo consultas con índices, manejo transacciones ACID para la reconciliación financiera y evito el problema N+1 con Spring Data JPA — procesando miles de registros diarios."

Preguntas típicas de bases de datos

¿Diferencia entre INNER JOIN y LEFT JOIN?

INNER devuelve solo las filas que coinciden en ambas tablas. LEFT devuelve todas las de la tabla izquierda y, donde no hay coincidencia, rellena con NULL — útil para listar clientes aunque no tengan facturas.

¿Para qué sirve un índice y cuándo NO usarlo?

Acelera lecturas al evitar escanear toda la tabla. Pero ralentiza las escrituras (hay que mantenerlo) y ocupa espacio; no conviene indexar columnas que casi no se consultan ni tablas muy pequeñas. Se indexan las columnas de filtros/JOINs frecuentes.

¿Qué significa ACID?

Las garantías de una transacción: Atomicidad (todo o nada), Consistencia (deja la BD en estado válido), Aislamiento (transacciones concurrentes no se pisan) y Durabilidad (una vez confirmada, persiste). Es lo que hace confiable una operación financiera.

Mensajería Cursillo de NATS (event-driven)

Cómo se comunican tus microservicios sin acoplarse. NATS es el sistema de mensajería que usaste en la plataforma de compras y recargas para que los servicios hablen por eventos.

Analogía: en vez de que un servicio llame por teléfono a otro (y espere), publica un anuncio (evento); quien le interese lo escucha. Emisor y receptor no necesitan conocerse ni estar activos a la vez — eso es estar desacoplados.

Los conceptos

Publish / Subscribe

Un servicio publica en un subject (tema) y todos los suscritos lo reciben. Uno-a-muchos.

Subject

El "canal" con nombre jerárquico (p. ej. pagos.recarga.ok). Admite comodines para suscribirse a grupos.

Queue groups

Varios consumidores comparten la carga: cada mensaje lo procesa solo uno del grupo (balanceo).

Request / Reply

NATS también soporta pedir y esperar respuesta (RPC ligero), no solo "disparar y olvidar".

JetStream

La capa de persistencia: guarda mensajes, reintenta y garantiza entrega (at-least-once). Para no perder eventos.

¿Por qué event-driven?

Desacopla, absorbe picos, agrega consumidores sin tocar al emisor y da resiliencia si algo se cae.

La idea en dos líneas

// El servicio de recargas PUBLICA un evento cuando algo pasa
nc.publish("pagos.recarga.ok", evento);

// Otro servicio (notificaciones) SE SUSCRIBE y reacciona
nc.subscribe("pagos.recarga.ok", msg -> enviarNotificacion(msg));

NATS vs. Kafka / RabbitMQ

NATS: ultraligero, rapidísimo y simple. Kafka: para grandes volúmenes y re-lectura de historiales. RabbitMQ: enrutamiento rico con colas.

Garantía de entrega

NATS "core" es at-most-once (rápido, sin persistir); con JetStream pasa a at-least-once con almacenamiento.

Dónde encaja: es el "sistema nervioso" entre tus microservicios en AKS. Complementa las REST APIs (síncronas) con eventos asíncronos para todo lo que no necesita respuesta inmediata.
Cómo lo cuentas tú: "Diseñé la comunicación event-driven de la plataforma con NATS: los microservicios publican eventos y otros los consumen de forma desacoplada (pub/sub y queue groups), lo que dio resiliencia, absorbió picos de tráfico y permitió agregar servicios sin tocar a los existentes."

Preguntas típicas de mensajería

¿Por qué usar mensajería en vez de llamadas REST directas?

Para desacoplar: el emisor no depende de que el receptor esté disponible ni de quién sea. Da resiliencia (si un servicio cae, el mensaje espera), absorbe picos y permite escalar consumidores. REST se queda para lo síncrono (necesito la respuesta ya); los eventos para lo asíncrono.

¿Diferencia entre pub/sub y queue group?

En pub/sub puro, todos los suscritos reciben cada mensaje (uno-a-muchos). En un queue group los consumidores comparten la carga y cada mensaje lo procesa solo uno — así escalas el procesamiento horizontalmente.

¿NATS garantiza que no se pierda un mensaje?

El NATS "core" es at-most-once (muy rápido, pero si nadie escucha, el mensaje se pierde). Para garantía de entrega usas JetStream, que persiste los mensajes y reintenta (at-least-once) — el que usarías para eventos críticos como un pago.

El diseño Arquitectura de software (hexagonal, DDD y trade-offs)

Este curso no te enseña algo nuevo: te enseña a nombrar lo que ya hiciste. Cuando migraste el monolito a microservicios event-driven, cortaste por dominios y conectaste servicios con NATS, estabas aplicando arquitectura hexagonal, DDD y patrón strangler fig — aunque en su momento no los llamaras así. En una entrevista de arquitecto, saber el vocabulario formal es la diferencia entre "hicimos una migración" y "diseñamos por bounded contexts, con el dominio aislado por puertos y adaptadores".

Analogía: el hexágono es una torre de control de aeropuerto. La torre (tu dominio: las reglas del negocio) no cambia aunque cambien las aerolíneas, los aviones o el sistema de radio. Solo le importan las puertas por donde entra y sale información (los puertos). Cada aerolínea, radio o radar es un adaptador intercambiable: cambias de PostgreSQL a Oracle, o de REST a mensajería, y la torre ni se entera.

¿Para qué sirve la arquitectura? (lo que realmente evalúan)

Acoplamiento

Que cambiar una pieza no obligue a tocar otras cinco. El monolito duele porque todo está pegado a todo.

Testabilidad

Poder probar las reglas de negocio sin base de datos, sin HTTP y sin Docker. Si necesitas levantar todo para probar una regla, el diseño está mal.

Reemplazabilidad

Cambiar Oracle por PostgreSQL, o REST por NATS, tocando un archivo y no todo el proyecto.

Velocidad de entrega

Equipos que despliegan sin pisarse. Tu −60% en tiempo de despliegue es, en el fondo, un resultado de arquitectura.

Autonomía de equipos

Un límite de dominio bien puesto = un equipo que puede decidir, desplegar y fallar solo (ley de Conway).

Coste del cambio

La arquitectura no se juzga por lo bonita, sino por cuánto cuesta el próximo cambio. Ese es el criterio real.

1 · Arquitectura por capas: la que ya usas (y dónde se rompe)

Es la de los cursos de Spring Boot y FastAPI: Controller → Service → Repository → BD. Funciona y es correcta para muchísimos casos. Su límite es la dirección de las dependencias: todo apunta hacia abajo, hacia la base de datos.

El síntoma

Tu clase de negocio tiene @Entity, @Column y anotaciones del ORM. La regla de negocio y el mapeo a la tabla viven en el mismo archivo: el dominio quedó casado con el framework.

La consecuencia

No puedes probar una regla sin levantar la BD, y migrar de ORM o de motor te obliga a tocar el corazón del negocio. Lo que hexagonal hace es invertir esa flecha.

// domain/Factura.java — no importa NADA de Spring ni de JPA
public class Factura {
    private final Long id;
    private final BigDecimal monto;
    private final LocalDate vence;
    private Estado estado;

    public boolean estaVencida(LocalDate hoy) {          // regla de negocio
        return estado == Estado.PENDIENTE && vence.isBefore(hoy);

    public void marcarPagada() {
        if (estado == Estado.PAGADA)
            throw new FacturaYaPagadaException(id);       // invariante protegida
        this.estado = Estado.PAGADA;
    }
}

// application/PagarFactura.java — puerto de entrada

    private final EventPublisher eventos;

    public PagarFactura(FacturaRepository repo, EventPublisher eventos) {
        this.repo = repo; this.eventos = eventos;

    public Factura ejecutar(Long facturaId) {
        Factura f = repo.buscarPorId(facturaId)
                        .orElseThrow(() -> new FacturaNoEncontradaException(facturaId));
        f.marcarPagada();                                // la regla vive en el dominio
        Factura guardada = repo.guardar(f);
        eventos.publicar(new FacturaPagada(guardada.id(), guardada.monto()));
        return guardada;
    }
}

5 · El equivalente en Python / FastAPI

Mismo diseño, sin interfaces obligatorias: en Python el puerto se declara con Protocol (o ABC).

# domain/factura.py — sin FastAPI, sin SQLAlchemy, sin Pydantic
from dataclasses import dataclass

@dataclass
class Factura:
    id: int | None
    monto: Decimal
    vence: date
    estado: Estado = Estado.PENDIENTE

    def marcar_pagada(self) -> None:
        if self.estado is Estado.PAGADA:
            raise FacturaYaPagada(self.id)
        self.estado = Estado.PAGADA

# domain/ports.py — el puerto de salida como Protocol
class FacturaRepository(Protocol):
    def buscar_por_id(self, id: int) -> Factura | None: ...
    def guardar(self, f: Factura) -> Factura: ...

# application/pagar_factura.py — el caso de uso, sin framework
class PagarFactura:
    def __init__(self, repo: FacturaRepository, eventos: EventPublisher):
        self.repo, self.eventos = repo, eventos

    def ejecutar(self, factura_id: int) -> Factura:
        f = self.repo.buscar_por_id(factura_id)
        if f is None:
            raise FacturaNoEncontrada(factura_id)
        f.marcar_pagada()
        guardada = self.repo.guardar(f)
        self.eventos.publicar(FacturaPagada(guardada.id, guardada.monto))
        return guardada

Y el adaptador FastAPI, donde Depends hace de "cableado" del hexágono:

8 · DDD táctico: los objetos que nombran tu dominio

Domain-Driven Design (Eric Evans) es el compañero natural de hexagonal: hexagonal te dice dónde poner el dominio, DDD te dice cómo modelarlo.

Entidad

Tiene identidad y ciclo de vida: una Factura sigue siendo la misma factura aunque cambien sus datos.

Value Object

Se define por su valor, no por un id, y es inmutable: Dinero(120000, COP), Periodo(desde, hasta).

Agregado & raíz

Un grupo de objetos que se modifica como una sola unidad transaccional. Solo se toca por su raíz (Factura manda sobre sus LineaFactura).

Repositorio

La colección del agregado, declarada como interfaz en el dominio — exactamente el puerto de salida de hexagonal.

Servicio de dominio

La regla que no pertenece a una sola entidad (p. ej. ConciliarPagos entre factura y transacción bancaria).

Evento de dominio

Algo relevante que ya ocurrió, en pasado: FacturaPagada. Es lo que publicas por NATS para que otros contextos reaccionen.

DDD estratégico (lo que más importa a nivel de arquitecto): el bounded context es la frontera dentro de la cual un término significa una sola cosa. "Cliente" en Facturación no es el mismo "Cliente" de Soporte Técnico: mismos datos, distinto significado y dueño. Un bounded context es el mejor candidato a microservicio — cortar por contextos (y no por capas técnicas) es justo lo que evita el "monolito distribuido".

9 · CQRS y arquitectura orientada a eventos

CQRS (Command Query Responsibility Segregation) separa el camino que escribe del que lee, porque casi nunca tienen la misma forma ni la misma carga.

Comandos (escritura)

Pasan por el agregado y respetan las invariantes: PagarFactura, AnularFactura. Consistencia fuerte, volumen bajo.

Consultas (lectura)

Van a un modelo optimizado para mostrar (una vista, un índice, una réplica). Volumen alto; puede tolerar consistencia eventual.

Eventos como pegamento

El comando publica FacturaPagada en NATS; otros contextos actualizan su propio modelo de lectura. Servicios desacoplados: no se llaman entre sí.

Event Sourcing (opcional)

Guardar la secuencia de eventos en vez del estado final. Da auditoría total, pero cuesta caro. CQRS no lo exige — confundirlos es un error clásico en entrevistas.

Cuándo aplicarlo: cuando lecturas y escrituras escalan distinto, o cuando la consulta necesita una forma que el modelo transaccional no da bien. Aplicarlo "porque sí" en un CRUD duplica el código y la complejidad sin ganancia.

12 · Trade-offs: cuándo NO usar hexagonal

Responder esto bien es lo que separa a un arquitecto de alguien que repite patrones. La respuesta madura nunca es "siempre".

No lo uses si…

Es un CRUD sin reglas, un MVP que quizá se bote en tres meses, o un script. Ahí hexagonal solo agrega carpetas, mapeos y ceremonia.

Sí lo usas si…

Hay reglas de negocio de verdad, varias entradas (REST + eventos + jobs), integraciones externas que pueden cambiar, o el sistema va a vivir años.

El coste honesto

Más archivos y un mapeo dominio↔entidad que hay que mantener. Lo pagas por adelantado a cambio de un cambio barato después.

Antipatrón: el "hexágono de cartón"

Interfaces con una sola implementación que replican exactamente los métodos del ORM y un dominio que sigue siendo anémico (puros getters). Tienes toda la ceremonia y ningún beneficio.

El círculo completo: defines el dominio aislado por puertos → Spring Boot / FastAPI aportan los adaptadores (REST, JPA/SQLAlchemy) → las reglas se prueban sin BD y SonarQube revisa el código → Docker empaqueta el servicio → Helm lo despliega en AKS → los bounded contexts se hablan por NATS con eventos de dominio. Cada curso de esta guía es una pieza de la misma arquitectura.
Cómo lo cuentas tú: "Diseño con el dominio aislado: arquitectura hexagonal, con las reglas de negocio en objetos puros, puertos declarados como interfaces y adaptadores para REST, persistencia y mensajería — así pruebo el negocio sin base de datos y cambiar de tecnología no toca el core. Para partir el monolito no hicimos un big bang: aplicamos strangler fig, cortando por bounded contexts de DDD y comunicando los servicios con eventos por NATS en AKS. El resultado fue 500 ms bajo alto tráfico, cero downtime y un 60% menos de tiempo de despliegue, con un equipo de 21 personas entregando de forma independiente. Preguntas típicas de arquitectura

¿Qué es la arquitectura hexagonal y qué problema resuelve?

Es un estilo donde el dominio (las reglas de negocio) queda en el centro, sin depender de ningún framework, y todo lo externo entra o sale por puertos (interfaces) implementados por adaptadores. Resuelve el acoplamiento entre negocio e infraestructura: puedo probar las reglas sin base de datos ni HTTP, y cambiar de motor de BD, de ORM o de transporte tocando solo el adaptador. La regla que lo gobierna es la inversión de dependencias: el dominio declara la interfaz, la infraestructura la implementa.

¿Diferencia real entre hexagonal, clean y onion?

Poca, y conviene decirlo así: las tres aplican la misma regla de dependencia hacia adentro. Hexagonal (Cockburn) usa el vocabulario de puertos y adaptadores y es la más simple. Onion (Palermo) lo dibuja como anillos concéntricos. Clean (Uncle Bob) prescribe más capas y nombra explícitamente entidades y casos de uso. En la práctica termino con la misma estructura de carpetas: dominio, aplicación e infraestructura.

¿Qué es un agregado y cómo eliges sus límites?

Un agregado es el conjunto de objetos que debe cambiar junto para no romper una regla, y se modifica solo por su raíz. El límite lo marcan las invariantes transaccionales: si "el total de la factura debe ser igual a la suma de sus líneas", entonces factura y líneas van en el mismo agregado. Lo que puede quedar consistente un segundo después (por ejemplo, actualizar un reporte) va en otro agregado y se sincroniza por eventos. La regla práctica: agregados pequeños, una transacción por agregado.

¿Cuándo NO usarías hexagonal?

En un CRUD sin reglas, en un MVP que puede desecharse, o con un equipo pequeño y un alcance corto. Ahí el coste (más archivos, mapeos dominio↔entidad, ceremonia) no se paga. También evito el "hexágono de cartón": interfaces con una sola implementación que copian el ORM y un dominio anémico — toda la complejidad sin ningún beneficio. La arquitectura es una inversión y debe justificarse por el coste del próximo cambio.

¿Cómo decidiste por dónde cortar el monolito?

Por bounded contexts de DDD, no por capas técnicas: cada servicio es un límite de negocio con su propio lenguaje y su propio dueño. Apliqué strangler fig: puse una fachada que enruta, extraje primero un contexto de alto valor y bajo acoplamiento, lo comuniqué con el resto por eventos (NATS) y luego apagué el módulo del monolito; repetir. Lo más difícil no fue el código sino separar los datos — si compartes la base, terminas con un monolito distribuido. Resultado: zero-downtime, 500 ms y −60% en tiempo de despliegue.

¿Qué es CQRS y cuándo lo aplicarías?

Separar el modelo de escritura (comandos que pasan por el agregado y respetan invariantes) del de lectura (vistas optimizadas para consultar). Lo aplico cuando lecturas y escrituras escalan distinto o cuando la consulta necesita una forma que el modelo transaccional no da bien; los modelos de lectura se alimentan de eventos y aceptan consistencia eventual. No lo confundo con Event Sourcing: ese guarda la secuencia de eventos como fuente de verdad y es una decisión aparte, bastante más cara.

¿Cómo documentas y comunicas una decisión de arquitectura?

Con un ADR por decisión relevante, versionado junto al código: contexto, decisión, alternativas consideradas y consecuencias (las buenas y las malas). Y para explicar el sistema uso el modelo C4, diciendo en qué nivel estoy: contexto → contenedores → componentes. Así la decisión sobrevive a la rotación del equipo: quien llegue en un año entiende por qué se hizo así y qué habría que reconsiderar si cambia el supuesto.

Aquí tienes una ventaja que casi nadie de tu competencia puede reclamar: viviste los dos mundos. Implementaste integraciones empresariales con Oracle SOA Suite, BizTalk Server y Oracle Service Bus para transacciones de alto volumen —y estás certificado en Oracle Service Bus—, y hoy diseñas REST APIs y arquitecturas event-driven a nivel experto. Los candidatos jóvenes solo saben REST; los veteranos a veces solo SOAP. Tú puedes hablar de la migración entre ambos, que es justo lo que necesita cualquier empresa con sistemas heredados.

Analogía: SOAP es enviar un documento notariado por correo certificado: sobre formal, formato obligatorio, firma, acuse de recibo y un contrato (el WSDL) que define exactamente qué se puede pedir. REST es hablar por mensajería instantánea: directo, ligero y basado en convenciones acordadas. Uno da garantías y ceremonia; el otro, velocidad y simplicidad.

Parte 1 · REST: los principios que debes recitar

Recursos, no acciones

La URI nombra cosas, en plural y sin verbos: /api/facturas/10245. El verbo lo pone HTTP, no la ruta (/getFactura es el error clásico).

Sin estado (stateless)

Cada petición lleva todo lo necesario; el servidor no recuerda nada entre llamadas. Por eso escala horizontalmente: cualquier réplica puede atender.

Verbos con semántica

GET lee, POST crea, PUT reemplaza, PATCH modifica parcialmente, DELETE borra. Respetarlos es la mitad de una buena API.

Códigos de estado

La respuesta se comunica por el código HTTP, no por un {"error": true} con 200. Un 200 con un error dentro rompe a todos los clientes.

Idempotencia

Repetir la misma petición debe dar el mismo resultado. Clave con reintentos: por eso PUT y DELETE son idempotentes y POST no lo es.

Contrato: OpenAPI

El esquema OpenAPI/Swagger es el equivalente moderno del WSDL: documenta, valida y genera clientes. Sin contrato no hay integración seria.

Por eso a los POST críticos se les pone una clave de idempotencia.

Versionado

Por ruta (/api/v1/facturas) es lo más común y explícito; también por cabecera. Lo importante es no romper a los clientes: añadir campos es compatible, quitarlos o renombrarlos no.

Paginación

?page=2&size=50 o paginación por cursor para listas grandes. Devolver 100.000 registros de una vez es el clásico problema de rendimiento en producción.

Errores consistentes

Un formato único para todos los errores (código, mensaje, detalle, id de traza). Estandarizado: Problem Details (RFC 7807).

HATEOAS

El nivel más alto del modelo de madurez de Richardson: la respuesta incluye enlaces a las acciones posibles. Se menciona en teoría y casi no se usa — dilo así y suena honesto.

Parte 2 · SOAP: el mundo del contrato estricto

Envelope

Todo va dentro de un sobre XML con Header (metadatos, seguridad) y Body (la operación). El formato es obligatorio, no convención.

WSDL

El contrato: describe operaciones, parámetros y tipos. Con él generas cliente y servidor automáticamente. Es el antepasado directo de OpenAPI.

XSD

El esquema que define y valida los tipos de datos. Validación estricta antes de procesar: en banca eso es una virtud, no un estorbo.

WS-Security

Seguridad a nivel de mensaje: firma digital, cifrado de partes del XML y tokens. Sobrevive aunque el mensaje pase por varios intermediarios (REST cifra el transporte, con TLS).

WS-* y transacciones

WS-AtomicTransaction, WS-ReliableMessaging: transacciones distribuidas y entrega garantizada estandarizadas. Es lo que REST nunca estandarizó.

SOAP Fault

Los errores tienen estructura propia dentro del sobre (faultcode, faultstring), independiente del código HTTP.

Una petición SOAP real, como las que atraviesan un bus de servicios:

Parte 4 · El bus de servicios (ESB) y qué fue de él

Es tu terreno: Oracle SOA Suite, BizTalk y Oracle Service Bus. Un ESB se pone en medio de todos los sistemas para que no se hablen directamente.

Qué hace un ESB

Enrutar mensajes al sistema correcto, transformar formatos (XSLT: el XML de un sistema al del otro), mediar protocolos (SOAP↔JMS↔archivo) y orquestar procesos de negocio de varios pasos.

Por qué apareció

Sin él, N sistemas necesitan N×N integraciones punto a punto. El bus las convierte en N conexiones: cada sistema habla solo con el bus.

Por qué cayó en desgracia

Se volvió un punto único de fallo y un cuello de botella organizativo: toda la lógica de negocio terminaba dentro del bus y un equipo central bloqueaba a todos los demás.

En qué se transformó

En API Gateway (seguridad, rate limiting, enrutado — sin lógica de negocio) más mensajería/eventos (NATS, Kafka). "Smart endpoints, dumb pipes": la inteligencia vuelve a los servicios.

Orquestación vs coreografía: en el ESB había un director que decía a cada sistema qué hacer y cuándo (orquestación). En event-driven cada servicio reacciona a los eventos que le importan, sin director (coreografía) — que es exactamente lo que hiciste con NATS en la migración a Nébula. Saber nombrar ese cambio te posiciona como arquitecto, no como programador.

Preguntas típicas de APIs e integración

¿Cuándo elegirías SOAP en lugar de REST?

Cuando el caso exige contrato formal y validación estricta (WSDL + XSD), seguridad a nivel de mensaje que sobreviva a intermediarios (WS-Security) o transacciones distribuidas estandarizadas. Es típico en banca, seguros y gobierno, o cuando el otro extremo ya expone SOAP y no lo vas a cambiar. Para todo lo demás —web, móvil, microservicios— REST o eventos: más ligero, cacheable y con mejor tooling.

¿Qué significa que una API sea idempotente y por qué importa?

Que repetir la misma petición produce el mismo resultado. Importa por los reintentos: si un cliente no recibe respuesta por un timeout, reintentará. GET, PUT y DELETE son idempotentes por definición; POST no. Por eso a las operaciones críticas —un pago— les pongo una clave de idempotencia que el servidor guarda: si llega repetida, devuelve el resultado anterior en vez de cobrar dos veces.

¿Diferencia entre 401 y 403? ¿Y entre 400 y 422?

401 Unauthorized: no sé quién eres (falta el token o no es válido) — autenticación. 403 Forbidden: sé quién eres, pero no tienes permiso — autorización. 400 Bad Request: la petición está mal formada (JSON roto, tipo equivocado). 422 Unprocessable Entity: la sintaxis es correcta pero falla una regla de negocio (una fecha de vencimiento anterior a hoy). Usarlos bien ahorra horas de depuración a quien consume la API.

¿Cómo versionas una API sin romper a los clientes?

Versión explícita en la ruta (/api/v1/) y regla de compatibilidad: agregar campos opcionales no rompe; quitar o renombrar sí. Cuando hay un cambio incompatible, publico v2 y mantengo v1 en paralelo con una fecha de fin de vida comunicada, midiendo qué clientes la siguen usando. El contrato OpenAPI y las pruebas de contrato me avisan si rompo algo antes de desplegar.

¿Qué es un ESB y por qué hoy se usan API Gateway y eventos?

Un ESB centraliza enrutado, transformación y orquestación para evitar integraciones punto a punto N×N. Funcionó, pero terminó concentrando la lógica de negocio y volviéndose un cuello de botella y punto único de fallo: un equipo central bloqueaba a todos. Hoy se separa: el API Gateway se queda con lo transversal (seguridad, rate limiting, enrutado) y la comunicación entre servicios pasa a eventos (NATS, Kafka), devolviendo la lógica a cada servicio — de orquestación a coreografía.

¿Cómo modernizas un servicio SOAP legacy que no puedes tocar?

Con una fachada REST delante: expone JSON al cliente moderno y traduce a SOAP hacia atrás, mapeando los SOAP Fault a códigos HTTP con sentido. Conceptualmente es un adaptador de arquitectura hexagonal. Le agrego caché, rate limiting y circuit breaker para que el legacy no se caiga con el tráfico nuevo, y esa fachada se vuelve el punto donde después reemplazo operación por operación (strangler fig) sin que el consumidor lo note.

¿Cuándo usarías gRPC o GraphQL en vez de REST?

gRPC entre microservicios internos donde importa la latencia y el volumen: binario, contrato fuerte en Protobuf y streaming. GraphQL cuando muchos clientes distintos necesitan combinaciones diferentes de los mismos datos y REST te obliga a multiplicar endpoints o a mandar de más. REST sigue siendo el defecto para APIs públicas: simple, cacheable y lo entiende todo el mundo.

¿Por qué dos tokens?

El access token viaja en cada petición: si lo roban, quieres que dure poco (5–15 min). El refresh token viaja rara vez, se guarda mejor protegido y sí se puede revocar porque el servidor lo tiene registrado.

Rotación del refresh

Cada vez que se usa, se emite uno nuevo y se invalida el anterior. Si aparece un refresh ya usado, es señal de robo: se revoca toda la familia de tokens de esa sesión.

5 · OAuth2 y OpenID Connect: quién es quién

OAuth2 = autorización

Un protocolo para delegar acceso: le das a una app permiso para usar un recurso tuyo sin darle tu contraseña. Responde "¿qué puede hacer esta app?".

OIDC = autenticación

Una capa sobre OAuth2 que añade el id_token (un JWT con la identidad). Responde "¿quién es este usuario?". Es lo que hay detrás de "Entrar con Google/Microsoft".

JWT = el formato

No es un protocolo: es el formato del token que OAuth2/OIDC suelen usar. Confundir los tres es el error más frecuente en entrevistas.

Authorization Code + PKCE

El flujo correcto hoy para web y móvil. El implicit flow está obsoleto; decirlo demuestra que estás al día.

Client Credentials

El flujo máquina a máquina: un servicio pide un token con su id y secreto, sin usuario de por medio. El habitual entre microservicios.

Proveedores

Entra ID (Azure AD), Keycloak, Auth0, Okta, Cognito. Lo normal es no implementar tu propio servidor de identidad: delegarlo es más seguro y más barato.

6 · Autorización: RBAC, scopes y el error del 401/403

RBAC

Control de acceso basado en roles: al usuario se le asignan roles (tesoreria, auditor, admin) y los permisos cuelgan del rol, no de la persona. Es lo que implementaste en el dashboard de reconciliación financiera.

Scopes

Permisos de grano fino sobre la API (facturas:leer, facturas:pagar). El rol dice quién eres en la organización; el scope, qué puede hacer esta aplicación en tu nombre.

ABAC

Control por atributos: no solo el rol, también el contexto (monto, país, horario, si el recurso es suyo). Necesario cuando "puede aprobar, pero solo hasta cierto monto".

401 vs 403

401: no sé quién eres (falta el token o es inválido). 403: sé quién eres pero no tienes permiso. Confundirlos es un clásico y se nota de inmediato.

8 · Los errores clásicos (con esto te filtran)

alg: none

Aceptar el algoritmo que dice el propio token permite firmar cualquier cosa. Fija el algoritmo esperado en el servidor y rechaza el resto.

No validar exp, iss, aud

Verificar solo la firma deja pasar tokens caducados o emitidos para otra API. Hay que validar los tres.

Datos sensibles en el payload

Va en Base64: es legible. Nada de contraseñas, tarjetas ni datos personales de más.

Tokens eternos

Un access token de 30 días es una llave maestra que no se puede quitar. Minutos para el access, y refresh rotativo.

Secretos en el repositorio

La clave de firma va en Key Vault o en un secret de Kubernetes, nunca en el código ni en appsettings.json. Y se rota.

Sin plan de revocación

Para "cerrar sesión en todos los dispositivos" hace falta lista negra, versión de token por usuario o refresh revocable. Tener respuesta a esto es lo que distingue.

El círculo completo: el usuario se autentica contra Entra ID → recibe un JWT firmado con RS256 → el API Gateway lo valida en el borde → cada microservicio (Spring Boot, .NET o FastAPI) verifica la firma con la clave pública del JWKS y aplica RBAC/scopes → los secretos viven en Key Vault, no en la imagen → y el pipeline con SonarQube detecta credenciales hardcodeadas antes de desplegar en AKS.
Cómo lo cuentas tú: "Aseguro APIs con JWT firmado en RS256: el servidor de identidad firma con la clave privada y cada microservicio valida con la pública del JWKS, sin llamadas extra — por eso escala. Para permisos aplico RBAC —lo implementé en el dashboard de reconciliación financiera— combinado con scopes por operación, distinguiendo bien 401 de 403. Y los secretos van en Key Vault, nunca en el repositorio. Cuando hace falta identidad corporativa, delego en OAuth2/OIDC con Entra ID en lugar de construir un servidor propio."

Preguntas típicas de autenticación y seguridad

¿Qué es un JWT y qué garantiza exactamente?

Un token con tres partes —header, payload y firma— codificadas en Base64 y separadas por puntos. El payload lleva claims (sub, exp, iss, aud, roles). La firma garantiza integridad y autenticidad: que nadie lo alteró y que lo emitió quien dice. No garantiza confidencialidad: el payload es legible por cualquiera, así que ahí no van datos sensibles. Su ventaja es que se valida sin estado, sin consultar la base de datos.

¿Sesión con cookie o JWT? ¿Cómo eliges?

Por la arquitectura. Sesión en servidor si es una app web de un solo dominio y necesito revocación inmediata — cerrar sesión es borrar la sesión. JWT si hay microservicios, clientes móviles o terceros: cada servicio valida por su cuenta y escala horizontalmente sin sesión compartida. El precio del JWT es que no se revoca fácil, y por eso el access token dura minutos y el refresh sí es revocable.

¿Cómo revocas un JWT antes de que expire?

Directamente no se puede: es válido hasta su exp. Se resuelve por diseño: expiración corta (5–15 minutos) para que la ventana de riesgo sea mínima, y refresh token revocable guardado en servidor. Si necesito corte inmediato, añado una lista negra por jti en Redis (solo hasta que expire, así no crece) o una versión de token por usuario: al cerrar sesión en todos los dispositivos, se incrementa y los tokens viejos dejan de validar.

¿Dónde guardas el token en el navegador y por qué?

Access token en memoria y refresh en cookie HttpOnly, Secure, SameSite=Strict. En localStorage es cómodo pero cualquier XSS lo lee y se lleva la sesión entera; la cookie HttpOnly es invisible para JavaScript, y el SameSite mitiga el CSRF que traen las cookies. Encima: HTTPS obligatorio, CORS restringido a orígenes conocidos y expiración corta.

¿Diferencia entre OAuth2, OIDC y JWT?

Son tres cosas distintas que suelen ir juntas. OAuth2 es un protocolo de autorización delegada: permite que una app acceda a un recurso tuyo sin conocer tu contraseña. OpenID Connect es una capa sobre OAuth2 que añade autenticación y el id_token con la identidad del usuario. JWT no es un protocolo: es el formato de token que ambos usan. En corto: OAuth2 = qué puedes hacer, OIDC = quién eres, JWT = cómo viaja esa información.

¿HS256 o RS256?

HS256 es simétrico: la misma clave firma y verifica, así que todo servicio que valide también puede emitir tokens. Sirve para un servicio único y controlado. RS256 es asimétrico: el servidor de identidad firma con la privada y los microservicios verifican con la pública, que publican en un endpoint JWKS. En arquitecturas distribuidas la respuesta correcta es RS256: separa emisión de validación y permite rotar la clave sin redistribuir secretos.

¿Qué es RBAC y cómo lo has aplicado?

Role-Based Access Control: los permisos se asignan a roles y los roles a personas, en vez de dar permisos uno por uno. Lo apliqué en el dashboard de reconciliación financiera, donde distintos perfiles ven y aprueban cosas distintas sobre datos sensibles. En APIs lo combino con scopes por operación (facturas:leer vs facturas:pagar), y cuando la regla depende del contexto —un monto máximo, el país, si el recurso es del propio usuario— se pasa a ABAC, decisión por atributos.

¿Cuáles son los errores de seguridad más comunes con JWT?

Aceptar el algoritmo que declara el token (alg: none) en vez de fijarlo en el servidor; validar solo la firma y olvidar exp, iss y aud, lo que deja pasar tokens caducados o emitidos para otra API; meter datos sensibles en el payload creyendo que va cifrado; tokens con vida de días; y secretos en el repositorio en lugar de Key Vault. Los reviso en revisión de código y el análisis estático del pipeline detecta credenciales hardcodeadas.

Paso 1 Docker & Dockerfile

Docker resuelve el clásico “en mi máquina sí funciona”: empaqueta tu aplicación con TODO lo que necesita para correr, de forma aislada y reproducible.

Analogía: un contenedor es como una lonchera sellada: adentro va tu comida (la app) y sus cubiertos (librerías, versión de Python/Java, config). La abras donde la abras —tu portátil o un servidor en Azure— adentro está exactamente lo mismo.

Los tres conceptos que debes distinguir

Dockerfile

la receta

Un archivo de texto con instrucciones para construir la imagen (qué base usar, qué copiar, qué instalar, cómo arrancar).

Imagen

El resultado de construir el Dockerfile. Es inmutable y se guarda en un registro (p. ej. Azure Container Registry).

Contenedor

Una imagen en ejecución. De una misma imagen puedes levantar 1 o 100 contenedores iguales.

Cómo se construye por “capas”

Cada instrucción del Dockerfile crea una capa que Docker cachea. Si no cambia, se reutiliza → los builds son rápidos. Por eso se ponen primero las cosas que cambian poco (dependencias) y de último el código.

Paso 2 Kubernetes (K8s)

Un contenedor está bien para una app; pero con decenas de microservicios, en muchos servidores, escalando y fallando en vivo, coordinarlos a mano es imposible. Kubernetes orquesta todo eso automáticamente.

Analogía: Kubernetes es el director de orquesta. Tú le dices el resultado que quieres (“quiero 5 copias de este servicio, siempre sanas y accesibles”) y él se encarga de reiniciar lo que se cae, repartir la carga y actualizar sin que el público note el cambio.

El modelo mental clave: estado deseado

No le das órdenes paso a paso; le entregas un manifiesto YAML que declara el estado deseado. Kubernetes lo reconcilia constantemente: si algo se desvía (un Pod muere), lo vuelve a poner como pediste. Eso es la auto-reparación.

Los objetos que debes nombrar

Pod

la unidad mínima

Envuelve uno o varios contenedores que viven juntos. Es lo más pequeño que Kubernetes despliega.

Deployment

réplicas + actualizaciones

Declara cuántas copias (réplicas) quieres de un Pod y gestiona las actualizaciones graduales (rolling updates).

Service

dirección estable

Da una IP/DNS fija para llegar a un grupo de Pods y balancea el tráfico entre ellos, aunque los Pods cambien.

Ingress

puerta de entrada

Enruta el tráfico HTTP/HTTPS desde afuera hacia el Service correcto (por dominio o ruta).

ConfigMap & Secret

config fuera del código

Guardan configuración y credenciales por separado, para no “quemarlas” en la imagen.

HPA (autoscaler)

escala solo

Las tres superpotencias (tu argumento de venta)

♻️ Rolling update

Levanta las réplicas nuevas y retira las viejas de a poco → zero-downtime.

🩹 Auto-reparación

Si un Pod se cae o no responde (health checks), lo reinicia o reemplaza solo.

📈 Autoescalado

Con el HPA, agrega réplicas cuando sube el tráfico y las quita cuando baja.

A fondo Kubernetes por dentro

Si el entrevistador va más allá de "¿qué es un Pod?", esto es lo que separa a alguien que usa Kubernetes de alguien que lo entiende.

Arquitectura del clúster

Un clúster tiene dos mitades: el control plane (el cerebro que decide) y los nodos (los músculos que ejecutan tus contenedores).

🧠 Control plane

decide y coordina

API Server (la puerta de entrada), etcd (la base de datos del estado), Scheduler (asigna Pods a nodos) y Controller Manager (reconcilia el estado deseado).

💪 Nodos (workers)

ejecutan los Pods

kubelet (agente que crea los contenedores), kube-proxy (redes/enrutamiento) y el container runtime (containerd) que realmente corre los contenedores.

En AKS, Azure gestiona el control plane por ti (no lo ves ni lo pagas como VMs); tú solo administras los nodos y tus aplicaciones.

Más objetos que vale la pena nombrar

StatefulSet

Para apps con estado e identidad estable (bases de datos, colas). A diferencia del Deployment, cada Pod es distinguible y persistente.

DaemonSet

Garantiza un Pod por nodo — típico para agentes de logs, métricas o seguridad.

Job / CronJob

Tareas que corren y terminan; el CronJob las programa (p. ej. una conciliación nocturna).

PV / PVC

PersistentVolume y su reclamo (PVC): almacenamiento que sobrevive aunque el Pod muera.

Namespace

Divide el clúster en espacios lógicos (dev / qa / prod, o por equipo).

Service types

ClusterIP (interno), NodePort (puerto del nodo), LoadBalancer (IP pública, vía Azure LB).

Salud, recursos y actualización sin cortes

Requests & Limits

requests = lo que el Pod reserva; limits = su tope. Evitan que un servicio ahogue a los demás.

Probes

readiness (¿listo para tráfico?), liveness (¿sigo vivo?) y startup (para arranques lentos).

Estrategia rolling

maxUnavailable: 0 + maxSurge: 1 = nunca bajas capacidad mientras actualizas.

apiVersion: apps/v1
kind: Deployment
metadata: { name: recargas-svc }
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # zero-downtime
  template:
    spec:
      containers:
        - name: app
          image: acr.azurecr.io/recargas:1.4.2
          resources:
            requests: { cpu: "250m", memory: "256Mi" }
            limits:   { cpu: "500m", memory: "512Mi" }
          readinessProbe: { httpGet: { path: /health, port: 8000 } }
          livenessProbe:  { httpGet: { path: /alive,  port: 8000 } }

kubectl scale deploy/recargas-svc --replicas=8
Pregunta típica: ¿qué pasa cuando un nodo se cae?

El control plane lo detecta (deja de recibir el "latido" del kubelet), marca sus Pods como perdidos y el Scheduler los reprograma en nodos sanos. Si tenías varias réplicas repartidas, el servicio ni se entera — eso es alta disponibilidad real.

Empaquetado Helm

Mantener a mano decenas de archivos YAML —y duplicarlos por cada entorno— es un dolor. Helm es el gestor de paquetes de Kubernetes: el "apt" o "npm" del clúster.

Analogía: un Chart de Helm es una plantilla parametrizable de tu despliegue. En vez de un YAML para dev y otro para prod, tienes una plantilla y un archivo de values por entorno: cambias valores, no copias archivos.

Los tres términos

Chart

el paquete

Conjunto de plantillas YAML + valores por defecto. Reutilizable y versionable.

values.yaml

la configuración

Los valores que rellenan la plantilla (imagen, réplicas, dominio). Uno por entorno.

Release

la instalación

Una instancia de un chart desplegada, con historial de versiones para hacer rollback.

Estructura de un chart

mi-servicio/
├─ Chart.yaml         # nombre y versión del chart
├─ values.yaml        # valores por defecto
├─ values-prod.yaml   # valores de producción
└─ templates/
   ├─ deployment.yaml # usa {{ .Values.replicas }}, {{ .Values.image.tag }}
   ├─ service.yaml
   └─ ingress.yaml

Comandos clave

helm install recargas ./mi-servicio -f values-prod.yaml
helm upgrade recargas ./mi-servicio --set image.tag=1.4.3   # nueva versión
helm rollback recargas 2      # volver a una versión anterior en segundos
helm list                     # ver releases instaladas
Cómo lo cuentas tú: "Empaqueté los microservicios como charts de Helm para desplegarlos de forma consistente en dev, QA y producción cambiando solo los values, con versionado y rollback inmediato — despliegues repetibles y seguros."

Preguntas típicas de Azure

¿Diferencia entre suscripción y grupo de recursos?

La suscripción es el límite de facturación y cuotas: todo lo que crees dentro se cobra ahí. El grupo de recursos es una carpeta lógica dentro de una suscripción para recursos que comparten ciclo de vida — se despliegan, se permisan y se borran juntos. Un patrón común es una suscripción por entorno (dev/QA/prod) y grupos por aplicación.

¿Qué es una managed identity y por qué usarla?

Es una identidad que Azure crea y rota automáticamente para un recurso (una app, un pod de AKS), de modo que pueda autenticarse contra otro servicio sin guardar credenciales. Elimina la contraseña del código y de las variables de entorno: el pod pide un token y accede a Key Vault o a la base de datos. Es la respuesta correcta a "¿dónde guardas el secreto?" — en ningún lado, uso identidad administrada.

¿Cuándo AKS y cuándo Container Apps?

AKS cuando necesito control fino: varios servicios, políticas de red, sidecars, operadores, afinidad de nodos o ya tengo cultura de Kubernetes. Container Apps cuando quiero correr un contenedor sin operar un clúster: escala a cero, menos costo fijo y mucho menos trabajo de plataforma. Como líder lo decido por el costo operativo: un clúster exige un equipo que lo mantenga.

Paso 4 GCP — Google Cloud, traducido desde Azure

Este curso parte de cero: no has trabajado con GCP. La buena noticia es que no necesitas empezar de cero de verdad — el 80% ya lo sabes. Contenedores, Kubernetes, CI/CD, identidades, redes y observabilidad son los mismos conceptos que operas en Azure; lo que cambia son los nombres y unas pocas decisiones de diseño que sí son distintas de verdad. Aquí traducimos pieza por pieza desde AKS, que es tu terreno, y marcamos con claridad las tres o cuatro cosas donde Google realmente hace algo diferente.

Analogía: cambiar de nube es como cambiar de aeropuerto, no de medio de transporte. Los aviones son los mismos (tus contenedores), las rutas son las mismas (Kubernetes), los procedimientos de vuelo son idénticos. Lo que cambia es la señalización, el nombre de las aerolíneas y en qué mostrador se factura. Si sabes volar, aterrizas en el otro aeropuerto sin problema: solo tienes que aprender a leer los letreros.

2 · IAM: un solo sistema de permisos

La fórmula

En GCP todo permiso se lee igual: quién (principal) + qué puede hacer (rol) + sobre qué (recurso o proyecto). Una sola frase, un solo sistema.

Tipos de rol

Básicos (Propietario, Editor, Lector — demasiado amplios), predefinidos (por servicio, los recomendados) y personalizados.

Cuenta de servicio

La identidad de una aplicación, no de una persona. Es el equivalente exacto de la managed identity de Azure.

Herencia

Los permisos bajan por la jerarquía: lo que das en la carpeta se hereda en todos sus proyectos. Igual que el ámbito del RBAC de Azure.

Workload Identity

Permite que un pod de GKE actúe como una cuenta de servicio sin manejar llaves. Mismo propósito que Workload Identity en AKS.

Lo que se simplifica

En Azure separas Entra ID (identidad) del RBAC de recursos. En GCP es un solo IAM para ambas cosas — un dolor de cabeza menos.

El error clásico del que llega de Azure: descargarse la llave JSON de una cuenta de servicio y meterla en el contenedor. Es exactamente lo que estabas evitando con managed identity. La forma correcta en GKE es Workload Identity: el pod obtiene credenciales temporales, sin archivos de llave que rotar ni filtrar.

3 · Red: aquí sí hay una diferencia real

La VPC de GCP es global

Una sola VPC abarca todas las regiones, con una subred por región. Los recursos de distintos continentes se hablan por IP privada sin configurar nada más.

La VNet de Azure es regional

Cada región necesita su propia VNet, y para conectarlas hay que hacer peering explícito. Es trabajo que en GCP simplemente no existe.

Firewall de VPC vs NSG

En GCP las reglas viven en la VPC y se aplican por etiquetas a las máquinas. En Azure el NSG se asocia a subredes o interfaces de red.

Balanceo global

Cloud Load Balancing da una sola IP anycast mundial que enruta al usuario a la región más cercana. En Azure, eso es Front Door; el Load Balancer normal es regional.

Aquí es donde tu experiencia con AKS se transfiere casi intacta. Kubernetes es el mismo: Deployments, Services, Ingress, ConfigMaps, HPA y kubectl funcionan igual. Lo que cambia es cómo se crea y se opera el clúster.

A cambio pierdes control — no puedes correr DaemonSets arbitrarios ni contenedores privilegiados, lo que rompe algunos agentes de seguridad o monitoreo. Zonal vs regional

Un clúster regional replica el control plane y los nodos en varias zonas: sobrevive a la caída de una. El zonal es más barato pero es un punto único de fallo. En AKS el control plane es gestionado y la HA por zonas se configura aparte.

Node Auto-Provisioning

GKE puede crear node pools solo cuando un pod no cabe en ningún nodo existente. AKS escala los pools que ya definiste, pero no te inventa uno nuevo.

Ingress

El Ingress de GKE levanta un Cloud Load Balancer global automáticamente. En AKS normalmente pones Application Gateway o un NGINX que tú administras.

Autoescalado

HPA (pods) es idéntico en ambas. El Cluster Autoscaler (nodos) también existe en las dos.

Versiones

GKE tiene canales de lanzamiento (rapid, regular, stable) y puede actualizarse solo. En AKS defines la versión y las ventanas de mantenimiento.

Y desde aquí, igual

Una vez tienes credenciales, kubectl, Helm, tus manifiestos y tus charts funcionan sin cambios. Ese es el verdadero seguro de portabilidad.

6 · Cloud Run: lo que AKS no te da

Qué es

Corre un contenedor sin clúster: le das la imagen y una URL HTTPS aparece. Escala a cero cuando nadie lo usa y pagas por request y por tiempo de CPU.

Por qué importa

Es la joya de GCP para servicios sueltos: sin nodos, sin parches, sin equipo de plataforma. El equivalente en Azure es Container Apps; para el modelo por función, Azure Functions ≈ Cloud Functions.

Cuándo Cloud Run

APIs con tráfico irregular, tareas por evento, prototipos, webhooks. Si el servicio pasa horas sin tráfico, escalar a cero cambia la factura por completo.

Cuándo GKE

Muchos servicios que se hablan entre sí, políticas de red, sidecars, procesos de larga duración, o cuando ya tienes cultura y herramientas de Kubernetes.

7 · Datos, mensajería y el resto de la plataforma

Cloud SQL

PostgreSQL, MySQL o SQL Server gestionados, con backups y réplicas. ≈ Azure Database for PostgreSQL. Es donde pondrías la BD de facturas.

BigQuery

El producto estrella de GCP: almacén analítico que consulta terabytes con SQL en segundos, sin servidores que administrar. ≈ Synapse, pero es la razón principal por la que muchas empresas eligen Google.

Firestore & Memorystore

Firestore: NoSQL de documentos ≈ Cosmos DB. Memorystore: Redis gestionado ≈ Azure Cache for Redis.

Spanner

Base relacional que escala horizontalmente conservando consistencia fuerte global. No tiene equivalente real en Azure; menciónalo solo si viene al caso.

Pub/Sub

Mensajería gestionada: publicador/suscriptor, at-least-once, reintentos y dead-letter incluidos. ≈ Service Bus / Event Hubs.

Secret Manager

Secretos versionados con permisos por IAM. ≈ Key Vault. Se consume desde GKE con Workload Identity, sin llaves en el contenedor.

Artifact Registry

El registro de imágenes y paquetes. ≈ ACR. Sustituyó al antiguo Container Registry.

Cloud Build

CI/CD gestionado que construye, prueba y despliega. ≈ Azure Pipelines. Cloud Deploy añade entornos y aprobaciones.

Cloud Logging & Monitoring

Logs, métricas y alertas (antes Stackdriver) ≈ Azure Monitor / Log Analytics. Cloud Trace ≈ Application Insights.

Conecta con lo que ya sabes: tú diseñaste la comunicación event-driven con NATS, que operabas tú mismo. Pub/Sub es esa misma idea pero gestionada: no administras servidores y traes reintentos y dead-letter de fábrica, a cambio de menos control sobre la latencia y de quedar atado al proveedor. Poder comparar los dos —lo que ganas y lo que cedes— vale más en una entrevista que haber usado cualquiera de los dos.

10 · Errores de novato que conviene evitar

Olvidar el proyecto

Casi todo comando necesita --project o un proyecto activo. Crear recursos en el proyecto equivocado es el tropiezo número uno.

Llaves JSON en el contenedor

Descargar la llave de una cuenta de servicio y montarla en el pod. Usa Workload Identity: sin archivos que rotar ni filtrar.

Creer que la VPC es regional

Vienes de VNets y asumes que necesitas una por región. En GCP la VPC es global; te sobra la mitad del diseño.

Elegir Autopilot a ciegas

Ignorar el egreso

Sacar datos de la nube y el balanceador global cuestan, y no siempre aparecen en la estimación inicial.

Preguntas típicas de GCP

¿Has trabajado con GCP?

Responde con franqueza y conviértelo en fortaleza: "En producción trabajo con Azure, sobre AKS. GCP no lo he operado en un proyecto real, pero conozco el modelo y las equivalencias — GKE, Artifact Registry, Cloud Build, Secret Manager, Pub/Sub — y las diferencias de fondo, como que la VPC es global o que el proyecto concentra facturación y agrupación. Como el grueso del trabajo es Kubernetes, Docker y Terraform, que son idénticos, la curva es corta." Inventar experiencia en nube se detecta en dos preguntas: basta con que te pregunten por la consola o por una cuota.

¿Qué es un proyecto en GCP y con qué se corresponde en Azure?

Es la unidad central: concentra facturación, cuotas, permisos y aislamiento, y todo recurso pertenece a exactamente uno. No equivale al grupo de recursos: se parece más a suscripción y grupo de recursos fusionados. Por eso lo habitual es un proyecto por aplicación y entorno — borrarlo elimina todo lo que contiene, lo que lo vuelve la unidad natural de limpieza. Por encima están las carpetas y la organización, equivalentes a los management groups y al tenant.

¿Diferencia entre GKE Autopilot y Standard?

En Standard administras los node pools y pagas por nodo, como en AKS. En Autopilot los nodos los opera Google y pagas por los recursos que piden tus pods. Autopilot quita casi todo el trabajo de plataforma, pero restringe DaemonSets y contenedores privilegiados, lo que puede chocar con agentes de seguridad o monitoreo. Elijo Autopilot cuando el equipo es pequeño y las cargas son estándar; Standard cuando necesito control fino del nodo. En AKS no hay un equivalente directo de Autopilot.

¿Cuenta de servicio o managed identity?

Son el mismo concepto con distinto nombre: la identidad de una aplicación, no de una persona, para que un servicio hable con otro sin contraseñas. En Azure es la managed identity; en GCP, la cuenta de servicio. En Kubernetes ambas se aterrizan con Workload Identity, que asocia la cuenta de servicio de la nube con la del pod. La mala práctica en GCP es descargar la llave JSON y montarla en el contenedor: eso es volver a tener una credencial que rotar.

¿Cuándo usarías Cloud Run en vez de GKE?

Cloud Run cuando quiero correr un contenedor sin operar un clúster: escala a cero, pago por uso y cero mantenimiento — ideal para APIs de tráfico irregular, webhooks o tareas por evento. GKE cuando hay muchos servicios que se comunican, necesito políticas de red, sidecars, procesos de larga duración o ya existe cultura de Kubernetes. El criterio de fondo es el costo operativo: un clúster exige un equipo que lo sostenga. Su par en Azure es Container Apps.

¿Qué diferencias hay en redes entre Azure y GCP?

La mayor es que la VPC de GCP es global: una sola red abarca todas las regiones con una subred por región, y los recursos se hablan por IP privada sin más. En Azure la VNet es regional y hay que emparejar redes entre regiones. Además el firewall en GCP vive en la VPC y se aplica por etiquetas, mientras que el NSG de Azure se asocia a subredes o interfaces. Y Cloud Load Balancing ofrece una IP anycast global; en Azure ese papel lo cumple Front Door.

¿Cómo migrarías una plataforma de AKS a GKE?

Primero delimito qué es portable y qué no: manifiestos, charts de Helm e imágenes son portables; lo atado al proveedor es la identidad, los secretos, el Ingress, el almacenamiento y la mensajería. Replico la infraestructura con Terraform, publico las imágenes en Artifact Registry, cambio la identidad de managed identity a cuenta de servicio con Workload Identity, muevo los secretos de Key Vault a Secret Manager y ajusto el Ingress al balanceador de GKE. Migro servicio por servicio, no en bloque —igual que hice con el monolito usando strangler fig—, con doble publicación de eventos durante la transición y un plan de vuelta atrás.

¿Pub/Sub o NATS?

Pub/Sub es gestionado: no operas servidores y trae reintentos, dead-letter y entrega at-least-once de fábrica; el precio es menos control sobre la latencia y dependencia del proveedor. NATS —que es lo que yo operé— es muy liviano y rapidísimo, y me daba control total, pero alguien tiene que mantenerlo y las garantías de entrega exigen JetStream. Si el equipo ya está en GCP y no quiere operar mensajería, Pub/Sub; si necesito latencia mínima o portabilidad entre nubes, NATS.

Paso 5 Calidad & seguridad del código: SonarQube y Kiuwan

En banca y gobierno, la calidad y la seguridad del código no son opcionales: se automatizan dentro del pipeline como un "quality gate" que bloquea el despliegue si el código no cumple.

Concepto base — SAST: ambas herramientas hacen análisis estático (Static Application Security Testing): revisan el código sin ejecutarlo, buscando bugs, vulnerabilidades y malas prácticas. Se contrasta con DAST, que prueba la aplicación ya corriendo.

SonarQube

Bugs, vulnerabilidades, "code smells" (malas prácticas), duplicación y cobertura de pruebas. Cuantifica la deuda técnica.

Quality Gate

Kiuwan

Enfoque

Plataforma de seguridad y calidad orientada a compliance. Fuerte en Code Security (SAST) y SCA (análisis de dependencias con vulnerabilidades conocidas).

La calidad Cursillo de Pruebas (Testing)

Probar es lo que hace que el "quality gate" tenga sentido: código que se puede cambiar sin miedo. Complementa tu sección de SonarQube/Kiuwan con las pruebas que alimentan la cobertura.

La pirámide de pruebas: muchas unitarias (rápidas, aisladas) en la base, menos de integración (varias piezas juntas) en el medio, y pocas end-to-end (todo el sistema) arriba. Rápido y barato abajo; lento y costoso arriba.

Los tipos y conceptos

Unitarias

Prueban una clase/método aislado. Rápidas; usan mocks para las dependencias.

Integración

Prueban varias piezas juntas (p. ej. servicio + base de datos real).

End-to-end (E2E)

Prueban el flujo completo como un usuario (UI → API → BD).

Mock vs. Stub

Mock: verifica interacciones (¿se llamó?). Stub: devuelve datos fijos. Aíslan la unidad bajo prueba.

Cobertura

% de código ejecutado por las pruebas. Útil como señal, no como meta ciega.

TDD

Red → Green → Refactor: escribes la prueba que falla, el código mínimo para pasarla, y luego limpias.

Una prueba unitaria (JUnit + Mockito)

@Test
void pendientes_devuelveSoloVencidas() {
  // Arrange — el repositorio es un mock
  when(repo.findByVenceBefore(any()))
      .thenReturn(List.of(new Factura("Luz", 50000)));
  // Act
  var result = service.pendientes();
  // Assert
  assertEquals(1, result.size());
  verify(repo).findByVenceBefore(any());
}

@SpringBootTest

Levanta el contexto de Spring para pruebas de integración del servicio real y sus beans.

Testcontainers

Arranca una base de datos real en un contenedor Docker durante las pruebas — integración fiel, no un simulacro.

Conecta con tu pipeline: estas pruebas corren en el paso de Test del CI/CD; su cobertura alimenta el Quality Gate de SonarQube/Kiuwan que decide si el código pasa a producción.
Cómo lo cuentas tú: "Aseguro la calidad con la pirámide de pruebas: unitarias con JUnit/Mockito, integración con @SpringBootTest y Testcontainers para BD real, e integradas al pipeline con cobertura que alimenta el quality gate — así el equipo cambia código con confianza."

Preguntas típicas de testing

¿Qué es la pirámide de pruebas?

Una guía de proporción: muchas unitarias (rápidas y baratas), algunas de integración, y pocas end-to-end (lentas y frágiles). Evita el "cono de helado" (demasiadas E2E), que es lento e inestable.

¿Diferencia entre mock y stub?

Un stub devuelve respuestas predefinidas para que la prueba avance; un mock además verifica que se le llamó como esperabas (interacciones). Ambos aíslan la unidad de sus dependencias.

¿Qué es TDD?

Test-Driven Development: escribes primero una prueba que falla (Red), luego el código mínimo para que pase (Green) y después refactorizas (Refactor). Fuerza un diseño testeable y evita sobre-ingeniería.

Curso Liderazgo y gestión de equipos

1 · Planear las asignaciones

Desglosa el trabajo (WBS)

Parte lo grande en tareas pequeñas y claras (1–3 días). Lo pequeño se estima mejor, se sigue mejor y motiva por avances visibles.

Prioriza

MoSCoW (Must/Should/Could/Won't) o matriz valor vs. esfuerzo: primero lo de más valor y menos esfuerzo.

Asigna por fortalezas y capacidad

Empareja la tarea con quien la hace mejor, respetando su carga real (no al 100%: deja holgura para imprevistos).

Mapea dependencias

Identifica qué bloquea a qué para secuenciar y evitar cuellos de botella.

2 · Estimar (sin adivinar)

T-shirt sizing

S/M/L/XL para una idea rápida de tamaño relativo antes de afinar.

Story points + Planning Poker

El equipo estima por complejidad relativa, en consenso — no en horas. Reduce el sesgo individual.

Estimación a 3 puntos (PERT)

(optimista + 4×probable + pesimista) / 6. Incorpora la incertidumbre.

Falacia de planificación

Tendemos a subestimar. Agrega buffer y compara con datos históricos.

Re-estima con velocity

Usa cuánto entregó el equipo en sprints pasados para proyectar lo que cabe en el próximo.

Estima en equipo

Quien hace el trabajo estima; el líder facilita, no impone.

3 · Seguimiento de tareas

Tablero Kanban

Visualiza el flujo (Por hacer → En curso → En revisión → Hecho). El estado se ve de un vistazo.

Límites WIP

Limita el trabajo en curso: menos multitarea = más se termina y más rápido.

Definición de Hecho (DoD)

Criterio claro de "terminado" (probado, revisado, documentado) para evitar el 90%-eterno.

Daily stand-up

15 min: qué hice, qué haré, qué me bloquea. Para sincronizar y destrabar, no para reportar al jefe.

Métricas

Burndown (trabajo restante), velocity (entregado por sprint), cycle/lead time (qué tan rápido fluye una tarea).

Gestiona bloqueos

Tu trabajo #1 como líder: remover impedimentos rápido para que el equipo avance.

4 · Manejo de personas

Delega con contexto

Delega el resultado y el porqué, no la microtarea. Da autonomía con un punto de control, no vigilancia.

Feedback con el modelo SBI

Situación → Comportamiento → Impacto: concreto y sin juzgar a la persona. Reconoce en público, corrige en privado.

1:1s regulares

Espacio quincenal por persona: cómo va, qué necesita, hacia dónde quiere crecer. Construye confianza.

Bajo desempeño

Abórdalo pronto y con datos: expectativa clara, apoyo, plan y seguimiento — no lo dejes crecer.

Motiva

Autonomía, maestría y propósito. Celebra avances y conecta el trabajo con su impacto real.

Resuelve conflictos

Escucha a ambas partes, enfócate en el problema (no en la persona) y busca el interés común.

RACI

Anticipa lo que puede salir mal (probabilidad × impacto) y ten un plan de mitigación.

¿Cuál es la diferencia entre Docker y una máquina virtual?

clave Una VM virtualiza un sistema operativo completo (pesada, arranca lento). Un contenedor comparte el kernel del host y solo empaqueta la app y sus dependencias: es mucho más liviano, arranca en segundos y es reproducible. Por eso encaja perfecto con microservicios.

¿Cómo logras un despliegue sin downtime?

Con rolling updates en Kubernetes: levanta réplicas nuevas y solo cuando pasan la readiness probe empieza a enviarles tráfico, retirando las viejas gradualmente. Sumado a liveness probes para auto-reparación. Así los usuarios nunca ven una caída — justo como en la plataforma de compras y recargas que migré.

¿Cómo migraste de un monolito WebLogic a microservicios?

Con un enfoque incremental tipo strangler fig: identificar dominios, ir extrayendo servicios uno a uno sin “big bang”, comunicarlos por eventos (NATS) y REST, contenerizarlos con Docker y desplegarlos en AKS con CI/CD. Esto permitió convivir con el monolito mientras se reducía el riesgo, logrando zero-downtime y −60% en despliegues.

Explica Pod, Deployment y Service.

Pod: la unidad mínima, envuelve el/los contenedores. Deployment: declara cuántas réplicas de ese Pod quiero y gestiona actualizaciones. Service: da una dirección estable y balancea el tráfico entre esos Pods aunque cambien. El Ingress los expone al exterior por HTTP/HTTPS.

¿Cómo escalas el sistema bajo un pico de tráfico?

Con el HPA (Horizontal Pod Autoscaler), que agrega réplicas según CPU/memoria, más Redis como caché para descargar la base de datos y APIs eficientes. Esa combinación fue la que sostuvo 500 ms de respuesta bajo alto tráfico.

¿Cómo manejas configuración y secretos?

Fuera del código y de la imagen: ConfigMap para configuración y Secret para datos sensibles en Kubernetes, y Azure Key Vault para credenciales. Así la misma imagen sirve para dev, pruebas y producción cambiando solo la configuración.

¿Qué hace un Dockerfile, capa por capa?

Define cómo se construye la imagen: FROM (base), WORKDIR, COPY de dependencias, RUN para instalarlas, COPY del código y CMD para arrancar. Cada instrucción es una capa cacheada: por eso las dependencias van primero (cambian poco) y el código de último (cambia seguido), para builds rápidos.

¿Por qué event-driven y no llamadas directas entre servicios?

Porque desacopla: el emisor publica un evento y no le importa quién lo consume. Si un servicio está caído, el mensaje espera; se pueden agregar consumidores sin tocar al emisor. Da resiliencia y escalabilidad — por eso usé NATS en la arquitectura de microservicios.

Técnicas y de producto

¿Cómo escalarías una plataforma de alto volumen?

Microservicios desacoplados, comunicación event-driven para absorber picos, caché (Redis), autoescalado en Kubernetes (HPA) y observabilidad (métricas, logs, trazas, SLOs) para atacar la latencia antes de que sea un problema.

¿Cómo incorporas IA (LLMs) que aporte valor real?

Foco en valor medible: un caso con ROI claro, con evaluación y guardrails (precisión, costo, alucinaciones), integrado como servicio. La diferencia entre un demo y algo productivo y confiable.

¿Cómo garantizas calidad y cero downtime?

Calidad en el pipeline (pruebas + quality gate que bloquea) y cero downtime con rolling updates + readiness/liveness probes en Kubernetes.

Microservicios vs monolito (explícalo simple)

Monolito: todo junto, fácil al inicio, difícil de escalar. Microservicios: servicios pequeños e independientes que se despliegan/escalan por separado. No siempre microservicios: se justifica con escala y velocidad de entrega.

¿Cómo aseguras la seguridad de datos (verticales financieros)?

Seguridad por diseño: secretos fuera del código (Key Vault), cifrado, RBAC y análisis SAST/SCA en el pipeline (OWASP). En banca trabajé bajo CMMI y cumplimiento.

¿Cómo manejas un incidente en producción?

Estabilizar (mitigar/rollback), comunicar con transparencia y luego postmortem sin culpa para la causa raíz. Mido el MTTR y convierto el incidente en aprendizaje.

¿Cómo balanceas calidad vs. velocidad?

No son opuestos a mediano plazo: la automatización da velocidad sostenible. Defino una calidad mínima no negociable y hago explícito el trade-off con el negocio.

¿Cómo mides la productividad del equipo?

Con resultados y flujo, no líneas de código: métricas DORA, cumplimiento de objetivos y calidad (defectos, cobertura). Valor con calidad de forma sostenible.

¿Por qué FastAPI y no Flask o Django?

FastAPI trae de fábrica lo que en Flask armarías a mano: validación con Pydantic, async nativo (ASGI) y documentación OpenAPI automática, con muy buen rendimiento. Django brilla con panel de administración y ORM integrado ("baterías incluidas"); para microservicios API-first con alta concurrencia de E/S, FastAPI es más liviano y directo. Elijo por el caso.

¿Cómo validas los datos de entrada en FastAPI?

Con Pydantic: defino un schema con los tipos esperados y FastAPI valida y convierte cada request. Si no cumple, responde 422 con el detalle, sin escribir esa validación. Con response_model también valido y serializo la salida.

¿Qué es Depends (inyección de dependencias) en FastAPI?

Es el mecanismo para "inyectar" cosas reutilizables en una ruta: la sesión de BD, el usuario autenticado, la configuración. Se declaran una vez y FastAPI las provee y las limpia por petición — desacopla y hace el código fácil de testear (puedes sobrescribir la dependencia con un mock).

¿Cuándo ayuda async/await y cuándo no?

Ayuda en trabajo I/O-bound (BD, otras APIs) con alta concurrencia: la ruta cede el control mientras espera, en vez de bloquear. No acelera lo CPU-intensivo, y si el driver de BD es síncrono esa llamada sigue bloqueando. Con Python real: FastAPI corre sobre Uvicorn (ASGI).

.NET / C# y frontend

¿.NET Framework o .NET 8? ¿Qué complica migrar?

.NET Framework (4.8) es solo Windows sobre IIS y está en mantenimiento; .NET 8 (LTS) es multiplataforma, mucho más rápido y pensado para contenedores, con Kestrel integrado. Lo que atasca una migración no es el lenguaje sino las dependencias solo-Windows: WebForms, WCF, System.Web y librerías de terceros sin versión moderna. Mi ventaja: viví la transición y hoy integro legacy .NET con APIs REST en AKS.

¿Cómo funciona la inyección de dependencias en ASP.NET Core?

El contenedor viene integrado. En Program.cs registro servicios con su ciclo de vida: Transient (uno por uso), Scoped (uno por petición — el habitual para servicios y DbContext) y Singleton (uno para toda la app), y el framework los inyecta por constructor. El error clásico: inyectar un Scoped dentro de un Singleton, que deja el DbContext capturado y corrupto.

¿EF Core o Dapper?

EF Core es el ORM completo: mapea clases a tablas, traduce LINQ a SQL y trae migraciones. Dapper es un micro-ORM para cuando necesito SQL a mano y máximo rendimiento: reportes pesados, consultas afinadas, procedimientos almacenados. Conviven: EF Core para el CRUD del dominio, Dapper para lo crítico. Y ojo con el N+1: se resuelve con Include.

¿Props o estado en React? ¿Y por qué no usar el índice como key?

Las props bajan del padre y son de solo lectura; el estado lo posee el componente y al cambiarlo se re-renderiza. Si el dato lo necesitan varios, se sube al ancestro común. La key es la identidad del elemento entre renders: con el índice, al reordenar o filtrar, React asocia el estado del DOM a la fila equivocada (se mezclan inputs, se pierde el foco). Usa un id estable.

APIs, integración y seguridad

¿Cuándo SOAP y cuándo REST?

SOAP cuando hace falta contrato formal y validación estricta (WSDL + XSD), seguridad a nivel de mensaje que sobreviva a intermediarios (WS-Security) o transacciones distribuidas estandarizadas — banca, seguros, gobierno, o cuando el otro extremo ya expone SOAP. REST para todo lo nuevo: web, móvil, microservicios. Nunca digo que SOAP sea obsoleto: sigue moviendo dinero real y probablemente lo mantiene quien me entrevista.

¿Qué es la idempotencia y por qué importa en una API?

Que repetir la misma petición dé el mismo resultado. Importa por los reintentos: ante un timeout el cliente reintenta. GET, PUT y DELETE son idempotentes; POST no. Por eso a las operaciones críticas —un pago— les pongo una clave de idempotencia que el servidor registra: si llega repetida, devuelve el resultado anterior en vez de cobrar dos veces.

¿Qué fue del ESB y qué lo reemplazó?

El ESB (Oracle Service Bus, SOA Suite, BizTalk) centralizaba enrutado, transformación y orquestación para evitar integraciones punto a punto N×N. Terminó concentrando la lógica de negocio y volviéndose cuello de botella y punto único de fallo. Hoy se separa: API Gateway para lo transversal (seguridad, rate limiting, enrutado) y eventos (NATS, Kafka) entre servicios — de orquestación a coreografía. Yo hice ese recorrido completo.

¿401 o 403? ¿400 o 422?

401: no sé quién eres (falta el token o no vale) — autenticación. 403: sé quién eres pero no tienes permiso — autorización. 400: petición mal formada (JSON roto, tipo equivocado). 422: sintaxis correcta pero falla una regla de negocio. Confundirlos se nota de inmediato y le cuesta horas de depuración a quien consume la API.

¿Qué garantiza un JWT y qué NO garantiza?

Garantiza integridad y autenticidad: que nadie alteró el contenido y que lo emitió quien dice, gracias a la firma. No garantiza confidencialidad: el payload va en Base64, no cifrado, y cualquiera lo lee. Por eso nunca van ahí contraseñas, tarjetas ni datos personales de más. Su ventaja es validarse sin estado: cada servicio verifica la firma con la clave pública del JWKS, sin consultar la BD.

¿Dónde guardas el token en el navegador?

Access token en memoria y refresh en cookie HttpOnly, Secure, SameSite=Strict. En localStorage es cómodo, pero cualquier XSS se lleva la sesión completa; la cookie HttpOnly es invisible para JavaScript y el SameSite mitiga el CSRF. Encima: HTTPS obligatorio, CORS restringido y expiración corta.

¿Diferencia entre OAuth2, OIDC y JWT?

OAuth2 = autorización delegada (qué puede hacer una app en tu nombre, sin darle tu contraseña). OIDC = capa sobre OAuth2 que añade autenticación y el id_token con la identidad (el "Entrar con Google/Microsoft"). JWT no es un protocolo: es el formato del token que ambos usan. Confundir los tres es el error más frecuente. Y el flujo correcto hoy es Authorization Code + PKCE; el implicit está obsoleto.

Nube: Azure y GCP

¿Has trabajado con GCP?

Respuesta honesta y con criterio: "En producción mi nube es Azure, sobre AKS. GCP no lo he operado en un proyecto real, pero conozco el modelo y las equivalencias —GKE, Artifact Registry, Cloud Build, Secret Manager, Pub/Sub— y las diferencias de fondo: la VPC es global, GKE ofrece Autopilot que no tiene par en AKS, y el proyecto concentra facturación y agrupación. Como el grueso del trabajo es Kubernetes, Docker y Terraform, que son idénticos, la curva es de semanas." Inventar experiencia en nube se cae en dos preguntas.

¿Qué es un proyecto en GCP y a qué equivale en Azure?

Es la unidad central de GCP: concentra facturación, cuotas, permisos y aislamiento, y todo recurso pertenece a uno solo. No es el equivalente del grupo de recursos: se parece más a suscripción + grupo de recursos fusionados. Por eso se usa un proyecto por aplicación y entorno — al borrarlo desaparece todo lo que contiene. Por encima están las carpetas y la organización, equivalentes a los management groups y al tenant.

¿GKE Autopilot o Standard?

Standard: administras node pools y pagas por nodo, como AKS. Autopilot: Google opera los nodos y pagas por lo que piden tus pods. Autopilot elimina casi todo el trabajo de plataforma, pero limita DaemonSets y contenedores privilegiados, lo que puede romper agentes de seguridad o monitoreo. Autopilot con equipo pequeño y cargas estándar; Standard cuando necesito control del nodo. Autopilot no tiene equivalente directo en AKS.

¿Diferencias de red entre Azure y GCP?

La grande: la VPC de GCP es global — una red abarca todas las regiones con una subred por región, y todo se habla por IP privada sin configurar nada. La VNet de Azure es regional y exige peering entre regiones. Además el firewall en GCP vive en la VPC y se aplica por etiquetas, mientras el NSG se asocia a subredes o interfaces. Para balanceo global, Cloud Load Balancing da una IP anycast; en Azure ese papel es de Front Door.

¿Managed identity y cuenta de servicio son lo mismo?

Sí, con distinto nombre: la identidad de una aplicación para que hable con otros servicios sin contraseñas. En Azure es la managed identity; en GCP la cuenta de servicio. En Kubernetes ambas se aterrizan con Workload Identity. La mala práctica en GCP es descargar la llave JSON y montarla en el contenedor: vuelves a tener una credencial que rotar y que se puede filtrar.

¿Cuándo Cloud Run y cuándo GKE?

Cloud Run para correr un contenedor sin operar un clúster: escala a cero, pago por uso, cero mantenimiento — APIs de tráfico irregular, webhooks, tareas por evento. GKE cuando hay muchos servicios que se comunican, políticas de red, sidecars o procesos largos. El criterio real es el costo operativo: un clúster necesita un equipo que lo sostenga. En Azure el equivalente de Cloud Run es Container Apps.

Arquitectura

¿Qué es la arquitectura hexagonal, en una frase?

Las reglas de negocio en el centro, sin depender de ningún framework, y todo lo externo entrando o saliendo por puertos (interfaces del dominio) que implementan adaptadores (REST, JPA/SQLAlchemy, NATS). La regla que lo sostiene es la inversión de dependencias: todos los import apuntan hacia adentro. El beneficio concreto: pruebo el negocio sin BD ni HTTP y cambio de tecnología tocando un adaptador.

Hexagonal, clean y onion: ¿son lo mismo?

En lo esencial, sí: las tres aplican la misma regla de dependencia hacia adentro. Hexagonal (Cockburn) habla de puertos y adaptadores; Onion (Palermo) lo dibuja como anillos; Clean (Uncle Bob) prescribe más capas y nombra entidades y casos de uso. Termino con la misma estructura: domain / application / infrastructure. Lo importante no es el nombre sino que el dominio no dependa del framework.

¿Qué es un bounded context y por qué importa para microservicios?

Es la frontera dentro de la cual un término significa una sola cosa: el "cliente" de Facturación no es el de Soporte. Importa porque un bounded context es el mejor candidato a microservicio: cortar por contexto de negocio (y no por capa técnica) da servicios con dueño claro y despliegue independiente. Cortar mal es lo que produce un monolito distribuido.

¿Cuándo NO usarías hexagonal ni microservicios?

En un CRUD sin reglas, un MVP desechable o un equipo pequeño sin problema de escala: ahí un monolito modular bien separado por dentro es la mejor decisión, y hexagonal solo agrega archivos y mapeos. La arquitectura se justifica por el coste del próximo cambio, no por moda. Y evito el "hexágono de cartón": interfaces con una sola implementación que copian el ORM sobre un dominio anémico.

¿Qué es un ADR y para qué lo usas?

Un Architecture Decision Record: un Markdown corto, versionado junto al código, con contexto, decisión, alternativas consideradas y consecuencias (buenas y malas). Sirve para que la decisión sobreviva a la rotación del equipo: quien llegue después entiende por qué se hizo así y qué reconsiderar si cambia el supuesto. Para explicar el sistema uso además el modelo C4 (contexto → contenedores → componentes).

Diseño System Design (diseño de sistemas)

La prueba estrella para roles de líder/arquitecto. No buscan la respuesta perfecta, sino tu forma de pensar: requisitos, trade-offs y comunicación. Aquí tienes un método repetible.

Regla de oro: no saltes a la solución. Aclara primero, dimensiona y razona en voz alta los trade-offs. Evalúan cómo piensas, no cuánto memorizas.

El método en 6 pasos

1 · Aclara requisitos

Funcionales (qué hace) y no funcionales (escala, latencia, disponibilidad, consistencia). Acota el alcance con el entrevistador.

2 · Estima (back-of-envelope)

Usuarios, QPS (lecturas/escrituras), almacenamiento, ancho de banda. Órdenes de magnitud, no exactitud.

3 · API & modelo de datos

Endpoints clave y esquema (SQL vs NoSQL según patrón de acceso y consistencia).

4 · Diseño de alto nivel

Cliente → API/gateway → servicios → datos, con balanceador, caché y colas.

5 · Profundiza (deep dive)

Elige 1–2 componentes críticos y detállalos (particionado, replicación, índice, cola).

6 · Cuellos de botella & trade-offs

Puntos únicos de fallo, escalado, consistencia vs disponibilidad (CAP), y cómo mitigar.

Piezas que siempre aparecen

Balanceo & escalado horizontal

Load balancer + réplicas sin estado. Escalar afuera, no arriba.

Caché

Redis/CDN para lecturas calientes; define invalidación y TTL.

Base de datos

Sharding (partición) y réplicas de lectura; SQL para transacciones, NoSQL para escala/flexibilidad.

Colas / mensajería

Kafka/NATS para desacoplar y absorber picos (procesamiento asíncrono).

CAP & consistencia

En partición eliges Consistencia o Disponibilidad; muchos sistemas usan consistencia eventual.

Observabilidad

Métricas, logs, trazas y alertas — cómo sabrás que funciona en producción.

Ejemplo resuelto: "Diseña una plataforma de notificaciones/mensajería a escala"

1) Requisitos: enviar SMS/WhatsApp/push a millones/día, alta disponibilidad, entrega garantizada, baja latencia. 2) Escala: ~10k mensajes/s en pico. 3) Diseño: API de ingesta → cola (NATS/Kafka) → workers por canal → proveedores externos, con reintentos y estado en base de datos. 4) Deep dive: idempotencia (no duplicar), rate-limiting por proveedor, dead-letter queue para fallos. 5) Trade-off: entrega at-least-once con deduplicación (sobre exactly-once) y consistencia eventual del estado.
Tu ventaja: ya construiste esto en la vida real (plataformas de alto tráfico, event-driven, 500 ms, zero-downtime). En un System Design, ancla en tus decisiones reales — te da una credibilidad que pocos candidatos tienen.

Preguntas típicas de diseño

¿SQL o NoSQL, cómo decides?

Por el patrón de acceso y las garantías: SQL para transacciones y relaciones fuertes (financiero); NoSQL para escala horizontal, esquema flexible o lecturas masivas. A menudo ambos (persistencia poliglota).

¿Cómo escalas lecturas vs. escrituras?

Lecturas: caché + réplicas de lectura + CDN. Escrituras: sharding por clave, colas para absorber picos y procesamiento asíncrono. Separar caminos (CQRS) cuando la carga lo exige.

¿Qué es el teorema CAP y cómo lo aplicas?

Ante una partición de red eliges Consistencia o Disponibilidad (no ambas). En alta escala se suele elegir disponibilidad con consistencia eventual; en financiero, consistencia fuerte. Lo clave es justificar el trade-off.

Los formatos típicos

Dinámica grupal

Resolver un caso en equipo. Buscan colaboración y liderazgo: aporta estructura, integra a otros y avanza a una decisión — sin apabullar.

Role-play

Simulan un 1:1 difícil (bajo desempeño, conflicto). Aplica SBI y escucha activa; enfócate en el problema y el plan.

Presentación

Exponer un caso/solución con estructura clara (problema → propuesta → impacto), seguro y conciso.

SJT (juicio situacional)

"¿Qué harías si…?" Elige la opción que equilibra resultado, personas y ética; evita los extremos.

Cómo destacar como líder (sin pasarte)

  • Escucha y suma: el mejor líder hace brillar al grupo, no lo monopoliza. Integra ideas y da crédito.
  • Estructura el caos: propón un método, timeboxing y un objetivo claro — eso ya es liderazgo.
  • Decide y avanza: ante el empate, ayuda al grupo a decidir con criterios, no a quedarse en el debate.
  • Datos y calma: mantén la compostura, apóyate en hechos y reconoce los buenos aportes ajenos.
